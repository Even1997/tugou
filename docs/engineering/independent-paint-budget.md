# 缓存预算、连续绘画与 AI 提前状态

## 范围与验收标准

本轮按 Compositor 对照审查的后续顺序处理缓存、绘画提交和 AI 主体选择状态。保留工程格式、逐笔历史与现有图层编辑行为。

- 解码图片缓存按 RGBA 估算控制在每个 Compositor 192 MiB 内；最近使用优先保留，淘汰后可重新读取，销毁后不残留缓存条目。
- PNG 编码移入 Worker，已编码图片直接提供预览缓存；与旧路径比较最终像素，验证半透明、蒙版、撤销、重做和重开。
- 上一笔提交时的新笔画排队，逐笔生成历史；切换工具、图层或编辑目标取消未提交笔画，不能串写。队列最多 32 笔，超限明确提示。
- 进入图片选区工具时检查模型、图片尺寸与可用内存；未就绪显示原因并禁用 AI，支持刷新。执行过程显示模型检查、加载及选区生成阶段。
- 独立测试目录与候选包验收通过，再更新原启动入口；不改写真实工程。

## 实现

`core/image-cache.cjs` 管理 LRU 与字节预算，替代 Compositor 的无容量 Map。原有过期修订清理继续保留。超预算单张图仍可显示但不留在缓存；进行中的解码复用同一个 Promise。

`raster-encoder.js` 与 `raster-encode-worker.js` 使用可转移 ImageBitmap、OffscreenCanvas 编码 PNG，并把位图交回缓存，减少重复解码。`use-painting.js` 在提交期间保存后续输入，按当前目标逐笔处理。数据仍逐笔保存为完整 PNG，没有改变持久化或撤销格式。

`subject-readiness.cjs` 复用本地组件检查与既有内存阈值。Windows 同时检查物理可用内存与提交余量；`image-worker.py probe` 只报告资源状态，不加载模型推理。界面在进入选区、重新聚焦及手动刷新时检查，无定时后台推理。运行阶段沿 IPC 传回，真实执行仍保留原有资源验证。

## 验证证据

证据位于 `app/test-results/paint-budget/`。源码桌面回归、包内回归、像素基准、真实本地组件探测、交付文件哈希分别保存在 JSON 和日志中；最终数量与耗时以 `metrics.json`、`delivery.json` 为准。

最终结果：210 项逻辑测试、源码 117 项桌面检查、包内 120 项桌面检查及 23 项 PS 风格选区补充检查通过，零渲染错误。包内基准每笔耗时中位数 365.85 → 264.05 ms（减少 27.8%），最大事件采样间隔 98.7 → 19.2 ms；源码样本中位数 393.5 → 270.65 ms。两次前后最终像素哈希均一致。

原启动入口已指向 `app/release/paint-budget/win-unpacked/Tugou.exe`；11 个构建文件在候选构建、dist 和 ASAR 间一致，连同 7 个后端文件共核对 18 项。更新期间 20 个原工程 JSON 哈希未变，没有重启用户窗口。旧 dist 和启动脚本保留于证据目录 `before/`，可回退。

基准为相同的 2048×2048 确定性纹理、8 笔绘制，包含绘制、编码、IPC 落盘和图片准备；记录逐笔耗时及 8ms 定时采样的最大事件间隔。最终像素 SHA-256 必须相同。中位数由第 4、5 个排序样本平均计算；早期原始报告的 medianMs 是上中位样本，汇总统一从原始 times 计算，未修改采样值。

256 级 alpha 测试确认：Worker PNG 与旧 PNG 往返逐像素一致，缓存位图与已保存 PNG 一致。最初直接对比内存画布与 PNG 重读出现 1 级颜色差异；旧路径也有相同浏览器舍入，未放宽新旧结果相等标准。

真实本地组件探测识别到 DirectML 和有效主体模型，但本机当次提交余量不足，提前显示不可用；未运行真实模型推理。界面就绪、阶段和输出测试使用明确的 IPC fixture，不能据此宣称实时抠图已成功。

## 风险与完成边界

- 192 MiB 是每个 Compositor 持有的解码图片估算，不是应用总内存上限；画布、在途编码、GPU 和历史资源另占空间。
- 仍逐笔编码完整 PNG，排队绘制可能等待提交；4MP 短样本不能代表 8K、大量图层、长期绘画或手写板表现。后续按实测决定是否需要局部修订与分块存储。
- AI 提前状态是当时的资源快照，不能保证稍后的推理成功；实际执行会再次验证。用户环境需配置本地组件并有足够内存后再验收真实推理。
- 本轮检查 Windows 1440px、1100px 工具栏；跨 DPI、Mac 和用户真实工程长时操作待验证。
