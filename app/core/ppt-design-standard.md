# 土狗 PPT 设计标准

本文依据用户对土狗的要求及 PPT 制作需求编写，适用于不同主题的演示文稿、视觉方案板和相关 Agent 工作流，不依赖外部设计 skill。

本文提供设计与制作规则，具体效果需要实际预览和用户选择验证。读取本标准不会自动生成内容、修改工程或授权付费操作；规则是否被执行仍取决于调用方 Agent。

## 1. 目标与判断顺序

制作让目标读者看得懂、愿意看，并且适合实际场景的 PPT。判断顺序为：事实与任务正确 → 内容结构清楚 → 视觉表达有特点 → 细节完整 → 能编辑和交付。前项不合格，不能靠后项弥补。

用户当次要求、真实品牌规范、已选定方向优先于默认建议。尊重已有作品中的有效设计，局部修改不擅自重做整套。

必须保留用户要求的信息。内容丰富不是缺陷：先分组、建立阅读顺序和调整图文比例；确实超出阅读容量时再分页，不以缩小文字、删除关键内容或填充装饰解决。

## 2. 设计前建立内容依据

### 土狗默认交互流程

新建或整体重设计 PPT 时，先完成大纲确认，再由用户选择设计或讲稿。这是土狗提供给 MCP 客户端的标准交互流程，不是要求用户自己记住并提醒的技巧。

1. **先写大纲，等待用户确认。** 核对受众、汇报目标、资料依据及页数或时长，整理整体大纲与逐页内容要点：页序、每页标题、核心观点及必要的资料说明。用 `ppt.create(layout:blank)`、`ppt.slide.create(layout:blank)` 准备空白页，`ppt.content.update.patch.text` 保存每页自由文本，不必拆成文字块。展示大纲并请用户确认内容；未确认前只修改大纲，不生成视觉方案、不制作正式幻灯片、不撰写完整讲稿。已有明确确认的大纲直接复用，不重复提问。
2. **大纲确认后，让用户选择下一步。** 询问“接下来先做视觉设计，还是先写讲稿？”，等待用户回答。不得默认同时执行或强制先设计；用户已明确选择或指定顺序时直接遵循，不重复询问。完成所选步骤后，再询问是否继续另一项；尚未选择的工作不自动执行。
3. **选择讲稿：按已确认大纲撰写。** 围绕每页要点补充解释、案例与上下页衔接，用 `ppt.slide.update.notes` 保存，使用 `ppt.open(panel:notes)` 展示供核对。讲稿不写入页面元素，不改现有设计，不清除 `content.text`，不为讲稿触发生图或视觉选型。写讲稿不要求先完成设计；缺失事实标注待核实，不编造数据。之后若用户选择设计，再进入下面的设计分支。
4. **选择设计：确认视觉范围，等待用户回答。** 询问要生成哪些视觉效果图：覆盖哪些代表页、需要几套方案、有无偏好或参考。可以给推荐项，例如“每套一张完整方案板，左侧规范，右侧封面、架构页和清单页”。已明确的范围或偏好直接复用。未回答前可查资料和完善已确认大纲的内容，不提交视觉生图，不制作正式画面。
5. **生成并展示方案板。** 按用户确认的数量、页型和真实内容生成，各方案使用相同内容，包含复杂页。每套一张图，左侧字体、配色、排版规范，右侧样页。先检查实际图片再展示，附简短适用说明和取舍；不使用空泛占位文案掩盖信息密度。
6. **确认视觉方向，等待用户选择。** 请用户选择方案或提出修改。修改后再次展示，直至用户明确选择；不得自行宣布推荐方案已经获选，也不能因为暂时未回复而默认通过。确认前不制作正式 PPT。
7. **按选定方案制作与验收。** 准备素材、制作可编辑整稿、逐页预览、保存与按需导出。保留已有讲稿，不因制作画面重写或清空讲稿。尚未选择写讲稿时不自动补写。根据选定样例检查一致性，报告仍未验证的显示环境。

内容大纲和实际幻灯片共用页面 ID 与顺序，不能维护另一套页序。`ppt.get` 无 slideId 返回大纲摘要，带 slideId 返回完整内容和元素；`ppt.open` 可使用 `sidebar:outline`、`panel:content` 查看草稿，`panel:notes` 查看讲稿。UI 每页只提供一个内容输入框；`content.text` 存在时（包括空字符串）是用户最新整页草稿，必须优先读取，不得被旧 blocks 覆盖。整页草稿不按换行自动拆成元素：AI 在获准制作后根据内容与布局整理可编辑文字，核对草稿全部落实后，才通过 `ppt.content.update.patch.text:null` 清除已落实草稿；省略 text 保留。`ppt.content.apply` 在整页草稿存在时返回 CONTENT_REQUIRES_LAYOUT，避免应用过期 blocks。内部内容文字块的 `id` 稳定，`elementId` 关联当前页的实际文字；写回 `blocks` 时保留 id/elementId/label/text，不写只读同步字段 baseText / draft。新建可编辑文字后，将原草稿块关联 elementId，移除同一元素的重复块，避免再次应用时重复创建。

### 获取 PPT 结果与截图验收

截图能力已经由 `ppt.preview` 提供，必须查看真实图片，不以 `ppt.get` 的元素数据、命令成功或导出成功代替视觉检查。它通过 MCP 返回 `content` 中的 `type:image`、`mimeType:image/png` 图片块，不是磁盘路径；同一响应的文本元数据包含目标文稿与页 ID、像素尺寸、revision 和加载状态。客户端需要支持 MCP 图片内容。

设计分支完成页面后按以下顺序检查：

1. 用 `ppt.get {presentationId}` 获取真实页 ID 和顺序；不要猜测 ID。先 `get_state` 获取当前 revision，检查是否已有演示；若有，先用 `ppt.present {action:"stop"}` 退出。
2. 调用 `run_command {command:"ppt.preview", args:{presentationId,slideId,maxSize:1440}, expectedRevision}`，获取指定页的真实 PNG。截图包含当前未保存的页面元素，仅幻灯片区域，不包含工具栏；content.text 草稿和 notes 讲稿不会被渲染进画面。maxSize 仅限制输出长边，不会放大窗口原始像素。
3. 查看图片，检查文字截断、重叠、对齐、留白、配图与风格一致性，同时用页面数据核对内容。核对返回页 ID、revision 与加载状态；截图失败或未就绪时不能宣称视觉验收通过。
4. 用 `ppt.present {action:"stop"}` 退出预览；需要修改时先读最新 revision，修正后重新截图。逐页重复，记录已检查页与问题；只截了部分页面就明确说明覆盖范围。此截图证明土狗当前渲染效果，不证明导出的 PPTX 在 PowerPoint / WPS 中完全一致。

用户只需要大纲或讲稿时，读取 content.text / notes 即可，不为凑截图提前制作画面。查看编辑界面可用 `ui.inspect` 和 `ui.capture`，幻灯片成品优先 `ppt.preview`。窗口隐藏或最小化返回 WINDOW_NOT_VISIBLE，需要先恢复；未支持后台离屏截图，不假报已拿到图片。不要求用户手工截屏作为默认流程。

草稿更新与画面更新是两个动作：`ppt.content.update` 只保存内容；结构化 blocks 已整理且无整页 text 草稿时，用户要求应用后用 `ppt.content.apply` 更新文字，保留位置、字体、阴影等样式。未关联块只能生成基础文字框，不能将其称为完成设计；图表和配图需求不会自动变成图像或图表。页面文字修改会同步到未改动的内容块；双方都改过时返回 CONTENT_CONFLICT，先比较草稿和当前元素并询问覆盖意见，不能擅自设 confirmConflicts。重新排版要作为独立操作，沿用已确认视觉方向，预览后检查内容完整与布局；锁定元素必须遵守锁定规则。

普通“帮我做 PPT”“用土狗做一下”“做完给我”等制作请求，只授权开始这套流程，**不等于允许跳过大纲确认、代选下一步，也不等于允许跳过视觉确认**。只有用户明确表示“不用视觉方案，直接制作”，或明确指定沿用某套已确认设计，才可省略对应步骤；执行时说明所依据的用户指示。既有 PPT 的局部文字、数据或排版修改不重新启动整套视觉选型。

MCP 初始化、状态与 PPT 命令发现响应均提供流程提醒；完整规则仍以本文件为准。当前由调用方 Agent 负责询问和等待，软件没有读取用户聊天答复的能力，不能把提醒描述成已确认状态或代码级阻断。

从用户内容和当前工程提取：受众、用途、现场演讲或独立阅读、页数或时长、已有品牌与素材、必须保留的事实。已有信息直接复用；缺失信息中，影响结论或事实的先确认，非关键视觉选择可标明假设继续探索。

先形成简短内容提纲。每页记录“读者需要知道什么、依据是什么、最适合怎样呈现”，不要直接把文章按段落塞入幻灯片。演讲稿和阅读稿可以有不同密度；不统一规定每页只能几个字。

| 内容关系 | 优先考虑的表达 | 避免 |
| --- | --- | --- |
| 选项比较 | 共用维度的对照表、并列图文 | 每个选项各说各话 |
| 时间与变化 | 时间轴、趋势图、阶段对照 | 无依据的箭头或走势 |
| 顺序与依赖 | 步骤、流程、分支关系 | 所有流程强制三步 |
| 比例与构成 | 有共同尺度的条形、构成图、表格 | 为好看扭曲比例 |
| 产品或场景 | 实物、截图、细节标注、使用过程 | 通用图库代替产品事实 |
| 经历或观点 | 具体叙述、照片、引述与解释 | 没有依据的感悟和口号 |

这是选择依据，不是固定页型库。标题、证据、图表和注释应共同回答本页的问题；复杂页面可有多个关联要点，但应能看出主次。

## 3. 形成可比较的候选方案

从提纲中选出同一组代表页，至少包含一张内容复杂的页面。各方案保留相同事实、文案和数据；不能用不同信息量、不同图片质量或删去难排内容的方式制造优势。

每套候选提交一份页面安排：标题与正文放在哪里、图片占多大面积、复杂信息怎样组织、其他页面如何沿用这些选择。用实际样例展示这些决定，不能只有风格名称或色板。

方案数量遵循用户要求。需要三套时，至少在构图、字体关系、图像表达、信息组织中的两个方面形成可见区别；仅换颜色不算不同方案。不能永久固定为“编辑式 / 信息式 / 叙事式”。

每套附一句具体的适用说明和取舍，例如“表格比较更充分，但封面照片面积较小”。用户应能根据自己的内容和偏好做选择，而不是从三个近似模板中猜测区别。

## 4. 视觉方案板

每个方案一张完整图片，左侧规范、右侧页面效果。默认左侧约四分之一，右侧约四分之三，可按内容调整；这只是起点，不是固定像素模板。

左侧包含方向说明、字体层级示例、色块与准确色值、版式和文案要点。右侧通常用封面加若干代表页，覆盖真实任务中的高密度页面和视觉重点，不只展示容易做漂亮的封面。表格、图表按需要出现；不能为凑齐区域编造内容。

可以放丰富文字与图片。方案板分区应让用户容易找到字体、色彩、文案与对应页面；实际字号由输出尺寸和查看场景决定。正常查看尺寸检查样例是否可辨，放大后核对具体文字和图表，不能只凭缩略图判断。

方案板是视觉提案，不是最终可编辑文件。同步保存文字版设计说明：颜色角色、字体及字重、层级比例、页边距、图片方向、选定页型和需要注意的实现限制。生图中的字体名称、色块标签、数字或页面比例不证明实际正确。

用户选择后再展开整稿；仅按第 2 节规定的明确跳过指示或已选设计省略对应确认，不能把一般制作请求解释成跳过授权。用户要求修改某一部分时保留已接受的部分，并明确本轮改动点。

## 5. 中文文案标准

- 先写文案并核对，再交给生图。标题概括本页内容，正文使用具体的人、事、时间、地点、费用和结果。
- 有证据支持的结论可作为标题；未得出的结论不能为了有力度提前写成事实。流程、预算、操作说明直接表达，不强加情绪价值。
- 不默认使用“把……变成……”“让……更……”“不止……更是……”等结构，不反复使用空泛抒情或宣传词。不是机械禁词，真实引述和有效品牌表达可保留。
- 情绪来自具体经历与细节；不编造个人故事、客户评价、业绩或来源。未知事实待确认，示例数据明确标为示例。
- 不把自然语言全部改成生硬栏目名。按语义换行，避免拆散词组、孤立标点、满页同长度句式，以及不必要的英文副标题。
- 删掉一句后若信息和语气都没有损失，优先删掉。必须保留的解释不能仅因“不够短”删除。

## 6. 排版、字体、色彩与图像

选定方向后，把页面尺寸、页边距、各类文字样式和图片位置记录为可复用参数。遇到长标题或内容较多的页面，调整该页布局并检查全套一致性，不逐个随意压缩字号。

从土狗字体库选择实际可用的字体，确认中文字符和所需字重；分别记录标题、正文、注释的字体、字号和行距。制作时检查长中文句子、英文、金额和日期的混排。不能以生图样例中的字体标签证明字体已正确加载。

使用用户选定方案的准确色值。检查文字在照片、底色和色块上的可读性；图表中的同一类别跨页使用相同颜色。没有必要把所有任务限制为相同配色，颜色变化也不能代替真正的方案差异。

图片先确认原始比例、清晰度和可裁切范围，再放入页面。人物面部、产品结构和需要解释的细节不得被误裁；透明图片检查边缘。多张图片一起使用时核对主体是否一致，生成的示意图不能被标注成用户真实照片或实测证据。

表格、数字、图片说明和页码使用各自一致的排版方式。不同内容页允许采用不同构图；不要把所有页面强制排成相同数量的卡片。实际演示或导出的页面效果是最终检查对象，不能只检查编辑器里的选中状态。

## 7. 生图提示词与土狗联动

每次生图任务准备以下输入，减少模型自行补写内容或猜测已有决定：

| 输入 | 必需内容 |
| --- | --- |
| 任务 | 生成整张方案板还是某个页面所需的素材，目标画幅与用途 |
| 内容清单 | 必须呈现的页面、准确文案、数据及示例标识 |
| 已确认设计 | 选定的字体建议、颜色、页面安排和参考图；未确认项注明可探索 |
| 修改范围 | 新生成或修改哪张图，哪些已接受的内容必须保留 |
| 输出检查 | 本次重点核对的文字、图片对应关系、比例及其他易错项 |

先检查共享素材和可用字体；已有适用素材优先复用。需要新图时围绕版面生成，例如为标题预留空白、统一人物或产品外观、按位置准备横竖版本。不能让每页单独生成后再勉强拼成一套。

选定后按需要调用土狗生图、抠图、超分、调色、素材库、图层及 PPT。按任务需要加工，不为展示能力强制经过所有工具。真实数据用确定性排版与图表制作，文字和可实现的形状保持可编辑；需要图片化的内容说明边界，不宣称应用具备尚未提供的能力。

工程保留原素材、加工结果和使用位置的关联；替换图片保留已确认的版面，不能无提示扩散到所有引用。运行操作先查当前对象与版本，保护手动编辑。生成与重试限于已授权范围；任务超时先查状态，不能通过更换 requestId 重复提交。

这些是供 Agent 遵循的工作流要求，不表示 MCP 自动编排。执行时通过命令目录确认当前能力，逐项检查任务结果、素材引用、排版、预览和导出，不以文档代替功能实现。

## 8. 检查、迭代与完成定义

每轮记录用户反馈、修改的页面或区域、前后版本及检查结果。事实错误和不可读内容先修复；视觉修改应回应具体反馈，例如标题太大、样例过小或图片与内容无关。生成新版本后核对原先正确的文字和数据，防止修复一处又改坏另一处。

| 关口 | 必须验证 |
| --- | --- |
| 内容 | 与原始材料核对，结论有依据，示例与事实区分，文案没有空泛填充 |
| 数据 | 数值、单位、合计、比例、图形尺度与标签一致；生图错误在正式制作中重建 |
| 页面 | 无溢出、遮挡、错字、图片错配和不可读文字；每页有清楚阅读顺序 |
| 整套 | 主题适合受众，视觉一致且构图有变化，没有无意义的重复和装饰 |
| 制作 | 字体可用、图片清晰，编辑与锁定行为符合预期，素材引用有效 |
| 导出 | 检查实际文件和可用预览；另查字体替换、换行、比例与特效，不把导出成功当显示一致 |

方案板完成定义：内容和示例标签正确、实际图片已查看、主要视觉缺陷已修正、可供用户比较；最终方向以用户选择为准。整稿完成定义：按所选方向完成全部内容、可用范围内逐页验证、交付可编辑工程及请求的文件，列清尚未验证的环境与限制。
